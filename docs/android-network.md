# 两端自动直连与实时行情（1.2.0）

## 启动慢的原因

1. 安卓原先在 onCreate 和 onResume 重复启动连接，每次都会清空接收状态、重新握手。
2. 旧 REST 逻辑先等主域名超时，之后才查询备用 CDN；重启进程后又要等待。
3. Windows 旧版只有单一主域名，显示首价还要等待日线请求及所有币种完成。
4. 原推送只订阅较慢的 `@ticker`，主 WebSocket 无法连接时退回轮询，无法满足连续成交价格显示。

## 1.2.0 如何连接

两端同时尝试：

- `wss://fstream.binance.com/market/stream`
- `wss://fstream.binance.me/market/stream`

以首条有效行情选择通道，取消另一个候选；每个合约订阅 `@aggTrade` 和 `@ticker`。成交消息驱动最新价，ticker 补充涨跌、高低等统计。界面将 50ms 内的更新合并，只显示最新值，避免每个网络包都重建界面。50ms 不是网络延迟承诺。Windows 1.2.1 将桌面显示节奏调整为 1 秒，首个价格立即显示，后台仍持续接收成交，避免密集行情让画面频繁跳动。

WebSocket 使用心跳和自动重连，切换自选会取消旧订阅；仅排序、改变透明度或配色不重建健康连接。安卓页面恢复也不重复断开。Windows 从休眠恢复后重新连接。

REST 主域名和动态 CDN 并行尝试。通过 DNSPod HTTPS DNS 查询 `fapi.binance.com` 当前 CNAME，只接受该精确名称对应的 `*.cloudfront.net`。HTTP 请求保留 `Host: fapi.binance.com`，TLS 使用并验证 CDN 主机名；不关闭证书校验、不写死 IP/CDN、不更换交易所或市场。

REST 提供首值、列表、K 线和断线补救。每 5 秒检查是否需要补救，健康且持续收到行情时不轮询价格。界面显示连接/重连状态，REST 备用数据不标作实时。慢响应按交易所成交时间及本地接收先后合并，避免新价格倒退。

## 无代理验证

2026-11-21 在开发机上显式使用不带代理的 Node HTTPS / WebSocket：

- BTC、ETH、MU、SNDK、SKHYNIX 首条成交约 0.9–1.0 秒。
- 连续 15 秒，各收到 221–850 条成交消息，5 个 REST 快照也全部成功。
- 动态压缩加载合约列表约 2.8 秒，共 956 项，MU/SNDK/SKHYNIX 均为 TRADING；K 线查询成功。
- 测试使用与桌面应用相同的网络模块，保持正常证书校验。安卓网络栈另用 OkHttp 显式 `Proxy.NO_PROXY` 检查。

成交可能成批到达，因此消息间隔不能直接当成端到端延迟。以上是本机结果，手机运营商和路由仍需真机确认；CDN 配置和域名可达性也可能变化。

## 网络设置与旧版

旧版 `.binance.vision/api/v3` 是现货接口，能直连不代表合约主域名也能直连。1.2.0 全部保持 USDⓈ-M 合约，不会退回现货。

默认选「自动连接」。若自己曾在「网络」填写代理，可切回自动连接；仍连接失败时点击「刷新」。代理仍为可选设置，只影响本应用。GitHub Pages 只发布静态官网和安装包，不中转行情。

## 悬浮窗和测试范围

安卓维持 `wrap_content`、40dp 币种栏和原有行距，长代码单行缩放/省略。网络错误使用短提示，不撑高浮窗。

桌面运行 `npm test`，安卓运行 `./gradlew testDebugUnitTest assembleDebug --no-daemon`。回归覆盖备用通道抢先成功、慢响应排序、未知涨跌格式化、请求取消、合约路径、限流和 CNAME 校验。Windows CI 另验证安装、覆盖升级、启动、卸载。本机重复执行修复后的安装模式逻辑 100 次，退出码为 0；未把静默安装测试当作人工逐页点击验收。
